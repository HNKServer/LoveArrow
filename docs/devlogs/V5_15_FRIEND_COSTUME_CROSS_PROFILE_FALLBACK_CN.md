# NPPS4 v5.15 好友服装与 CN/GL 跨服回退修复说明

## 本版基线

本版基于已经恢复正常启动和换装契约的 **v5.14-costume-contract-stability-fix** 继续修改。

`BUILD_ID`：`v5.15-friend-costume-cross-profile-fallback`

不改动 v5.14 已确认的普通持有卡语义：

- 没有真实换装绑定时，`unit/unitAll` 不发送 `costume`；
- 有真实 `UserCostumeDress` 时才发送服装对象；
- 不发送 `"costume": null`；
- 原始卡面不占用衣柜衣装；
- 不增加全衣柜预读或常驻用户缓存。

## 好友服装显示根因

好友搜索、好友资料、排行榜、问候和演唱会助战中的中心卡并不只是“对方主力队伍中央卡的原始外观”。后期 SIF 协议把这类响应拆成两层：

1. 等级、属性、技能和 Live 队长技能等数值来自对方主力队伍的中央卡；
2. `center_unit_info.costume` 是对方导航伙伴/看板成员的显示外观。

honoka-chan 的好友搜索和个人资料实现也采用这一结构：主力中央卡负责数值，而 `costume` 使用导航伙伴外观。

v5.14 只在被选为数值中央卡的那张卡上查询换装，因此即使好友的导航伙伴已经换装，也会返回数值中央卡的原始卡面。CN/GL 共用账号后，换装绑定又按 Profile 保存；接收方查看好友时只查询接收方 Profile，更会遗漏好友在另一 Profile 中设置的绑定。

## v5.15 的好友服装投影

好友、资料与助战等社交响应现在统一执行：

1. 数值卡优先使用对方当前主力队伍中央卡；
2. 显示服装优先使用对方导航伙伴/看板成员；
3. 先查询接收方当前 Profile 中该导航伙伴的换装绑定；
4. 当前 Profile 没有可用绑定时，再定点查询另一 Profile 的同一张持有卡；
5. 只有服装 Master、签名资源及登记记录都能被接收方客户端安全识别时才发送；
6. 不可识别的跨服服装不会被删除，也不会把未知 ID 发给客户端；
7. 没有可移植换装时，回退到接收方能显示的原生伙伴外观或安全中央卡外观。

好友资料和好友邀请界面的客户端服装开关属于**查看方显示开关**。因此服务器需要把对方真实选择的显示外观发送过去，而不能因为对方自己的本地服装开关状态而隐藏数据。

## CN/GL 独有卡安全回退

共享账号和好友图不代表 CN 与 GL 的不可变 Master 数据完全相同。本版为所有跨用户卡牌响应使用统一规则：

- 主力中央卡在接收方不存在：尝试导航伙伴；
- 导航伙伴也不存在：按稳定顺序寻找该用户实际拥有、且接收方支持的其他活动卡；
- 不虚构卡牌所有权，不把独有 `unit_id` 强行映射成无关卡；
- 奖励称号、背景、饰品和 SIS 等附属 ID 继续按接收方 Master 过滤；
- 没有任何真实持有卡可安全投影时，好友列表隐藏该不安全条目，好友搜索/个人资料返回普通游戏错误，而不是发送 `null` 或未知 ID。

### 演唱会助战

演唱会比纯显示还要求队长技能可计算，因此候选卡还必须满足：

- Unit Master 在接收方存在；
- 引用的默认队长技能 Master 在接收方存在；
- 卡牌完整数值可以在接收方 Master 中计算。

`/live/partyList` 和 `/live/play` 现在调用同一个确定性候选选择函数。这样邀请界面显示的安全助战卡，与真正开始 Live 时用于队长技能计算的卡保持一致，不会出现“列表能显示、开歌时却因独有卡崩溃”的漂移。

## 内存与查询策略

按照原版 NPPS4 的处理风格，本版没有增加长期内存预读：

- 不预载用户整个衣柜；
- 不预载用户全部换装绑定；
- 不建立进程级或 Session 级用户服装缓存；
- 只针对正在生成响应的那一张导航伙伴卡查询绑定；
- 当前 Profile 一次定点查询，必要时另一 Profile 再一次定点查询；
- Master 数据仍复用 NPPS4 原有的单请求 `BasicSchoolIdolContext.cache`。

内存不会变成“在线用户数 × 衣柜规模”的长期占用。

## 涉及接口

统一使用导航伙伴显示服装和跨服安全回退的路径包括：

- `friend/list`
- `friend/search`
- `profile/profileInfo`
- `live/partyList`
- `live/play`
- 排行榜中心成员
- 问候/公告相关中心成员

## 数据兼容

- 不需要数据库迁移；
- 现有 CN/GL 衣柜和换装绑定保留；
- 两个 Profile 的衣柜没有合并；
- 跨 Profile 只读取可安全显示的既有绑定，不复制、删除或改写来源数据；
- v5.14 的 JSON `null` 防护和服装单一占用规则保留。

## 建议真机复测

1. 同一 Profile 的好友设置导航伙伴服装，另一账号在好友资料中切换服装显示；
2. 在演唱会好友邀请界面确认好友服装能显示并可切换；
3. CN 账号设置服装后用 GL 查看，再反向测试；
4. 好友主力中央卡与导航伙伴不是同一张卡时，确认数值/队长技能来自主力中央卡，而外观来自导航伙伴；
5. 将独有卡设为主力中央卡，确认另一客户端回退到真实拥有的共同卡且能正常开歌；
6. 将独有卡设为导航伙伴，确认不可用原卡不会泄漏未知 ID；若其换装服装在另一端存在，则只显示可安全识别的服装；
7. 确认自己的普通卡牌换装、`SET`、脱下和衣柜登记行为未回归。
